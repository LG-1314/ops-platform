# 运维全维度管理平台 · 全维度理解 + 检查报告

> 审查范围：`F:\ops-platform` 整个仓库（docs/ 10 份规范 + src/ 91 个源码文件）
> 审查方式：逐文件通读文档与源码，并用子代理交叉核验；对高危/易错点（命令注入、凭据加密、CORS/鉴权、配色、死代码、诊断只读性）均**亲自读源码坐实**，不盲信推断。
> 结论先行：代码真实可运行、架构自洽、SSH/DB/云/K8s/终端均为**真连实现**，诊断引擎真跑本机只读命令，凭据 AES-256-GCM 加密不落明文。但存在 **1 个高危安全漏洞、多处文档与实现严重冲突、若干功能缺陷与死代码/死依赖**。

---

## 0. 项目全貌理解（"它到底是什么"）

一个 **Electron 28 桌面运维工作台**（Windows 优先），形态为「Electron 壳 + Vite/React 前端 + Express 能力总线」：

- **Electron 主进程**（`src/main/main.ts`）：拉起 Express（`127.0.0.1:8787`）、注册 `ops://` 协议、单实例锁、把前端 API 请求经 IPC 转发给 Express。
- **能力总线**（`src/server/`，Express 4）：18 个 router + 21 个 service，统一信封 `{code,data,message}`，`code=0` 成功。
- **诊断引擎**（`src/diagnostics/`）：跨平台**只读**系统体检，`execSync` 固定命令字符串，对象恒为「运行本 App 的本地机」。
- **前端**（`src/renderer/`）：React 18 + MUI 5 + HashRouter，14 个页面，深色主题写死 `buildTheme('dark')`，API 经 `opsApi.request`（IPC）调用。
- **存储**：内存 Map（`memoryStore`）+ JSON 文件持久化（`persist.ts` → `userData/store.json` + `ops-key.json`），**未用 SQLite**。

数据闭环：前端 → `opsApi.request`（IPC）→ 主进程 Node `http` → `127.0.0.1:8787` Express → service →（诊断/SSH/DB/云/K8s/终端真连 or 内存存储）。

## 2. 全方位检查（按维度）

### 2.1 文档与实现一致性（严重）

仓库里 **4 套互相冲突/过时的规范**，无单一真源：

| 文档 | 描述形态 | 与代码偏差 |
|------|---------|-----------|
| `system_design.md` | light 主题、emoji 状态、内存存储、无 SSH/DB/云主机、计划 `router.tsx`+`appStore`+`useApi` | **整体过时**（代码已是 dark、无 emoji、有 ssh/db/cloud、无 router.tsx/Zustand） |
| `ARCHITECTURE.md` / `ADR-001` | 升级到 SQLite + `@kubernetes/client-node ^1.4.0` + 各 SDK 版本 | SQLite **未落地**；k8s 实际 `^1.1.2`；mysql2/pg/ioredis 版本均低于文档 |
| `PRD.md` / `Spec.md` | v2.0 暗色 Grafana 风、SQLite、SSH 主机深度采集、**通知渠道 P0**、Web 终端 | 通知渠道**缺失**；SQLite 未落地；诊断仅本机（与 PRD「SSH 免 Agent 深度采集」背离） |
| `PLAN.md` | 更早期 v1（ECharts/SQLite/node-cron） | 已偏离，仅作背景参考 |

额外不一致：
- **README 机制描述错误**：称前端「`window.opsApi.apiBase → http://127.0.0.1:<port>/api` REST 直连」。实际前端 REST 走 `opsApi.request`（IPC→主进程 Node http），`apiBase` 仅用于 WebSocket 终端地址推导。机制描述与代码不符（低危，但会误导维护者）。
- **`app://` vs `ops://` 命名错乱**：README 与 `main.ts` 注释写「自定义协议 `app://`」，代码实际注册的是 `ops`（且主窗口实际用 `loadFile(file://)`，协议导航根本没用上）。
- **mermaid 图过时**：`class-diagram.mermaid`/`sequence-diagram.mermaid` 只画了 system_design 的 11 个旧 service，缺 ssh/db/cloud/credentials/alert-rules/terminal/k8s 等。
- **`dev` 脚本**：`system_design` T01 验收要求 `npm run dev` 同时起 Vite+Express；实际 `package.json` 的 `dev` 仅 `vite`，Express 需另起。README 与代码一致，是 system_design 过时。

### 2.2 安全（1 高危 + 3 中危）

1. **【高危】命令注入** — `src/server/services/monitorService.ts:33-35` `pingProbe`：
   ```ts
   const cmd = isWin ? `ping -n 1 -w ${timeoutMs} ${host}` : `ping -c 1 -W 2 ${host}`
   exec(cmd, ...)
   ```
   `host` 来自用户录入的 `asset.host`，**无校验/转义**，且后台 30s 监控会遍历所有资产执行。构造 `host="1.2.3.4; calc"` 即可在用户机器执行任意命令；叠加 §2.2-2 的开放 API，本地恶意网页可注入资产触发 **本地 RCE**。→ 改为 `execFile('ping', [...])` 数组参数或白名单校验。

2. **【中危】全开 CORS + 零鉴权** — `server/index.ts:47` `app.use(cors())`（无 origin 限制），所有 `/api` 无 auth 中间件，Express 绑 127.0.0.1。本机任意网页可 `fetch('http://127.0.0.1:8787/api/...')` 读写（建凭据、删资产、注入资产触发 §2.2-1）。→ 至少限制 origin 为本地、或对写接口加轻量令牌。

3. **【中危】渲染进程安全放松** — `main.ts:326` `webSecurity:false` + `no-sandbox` + `disable-gpu`。对受限 Windows 属"标准取舍"，但 `webSecurity:false` 关闭同源策略，叠加 IPC 模型需评估。可接受的运维内网工具取舍，建议加注释说明并尽量收窄。

4. **【中危】终端 WebSocket 无鉴权** — `server/index.ts:102` `/api/terminal` 仅凭 `credentialId` 查询参数直连目标机，无用户认证；同机任意进程可借 `credentialId` 开 SSH 终端。

5. **【低危】凭据密钥与密文同目录** — `crypto.ts` 把 `ops-key.json` 与 `store.json` 同放 `userData`；能读该目录者可用密钥解密全部凭据（本地单用户威胁模型下可接受，但非系统密钥环）。注意：本项目**未用** ADR-001 约定的 `safeStorage`，而用 Node `crypto` AES-256-GCM（设计取舍，功能正确，密钥管理较弱）。

### 2.3 功能完整度 / 正确性（2 个严重 bug + 多处占位）

1. **【严重】CPU 告警规则永不触发** — `sshService.ts:66-117` `parseMetrics` 从不写 `cpuUser/cpuSystem/cpuIdle`（且 `collectMetrics` 根本不执行 CPU 采集命令，只跑 uptime/free/df）。`alertRuleService.metricValue` 对 `cpu` 判定 `cpuIdle == null → return null` 跳过。结果：所有 `metric:'cpu'` 告警规则静默无效；`Hosts.tsx` 的 CPU 进度条因守卫也永不可见。**SSH 采集缺 CPU 是一个真实功能缺口。**

2. **【严重】诊断/体检与目标资产脱节** — `diagnostics/run`、`patrols/run` 实际只跑**本机** `diagnose()`；`engine.ts` 用 `platform()/hostname()` 取本机信息。PRD 把「SSH 免 Agent 深度采集」列为头号 P0，但「系统体检」页只体检运行 App 的这台机器，与目标资产无关（远程指标需走 Hosts 页的 SSH 采集，且仍缺 CPU）。定位/文案存在误导。

3. **【占位/缺口】** 通知渠道（飞书/钉钉/企企/邮件）**完全缺失** —— Spec 列 P0 护城河，实际无 `/api/notification-channels`，告警触发后无对外推送。
4. Guardrails / Dolores / 报告 PDF / 知识自维护 / 自动化 CI/CD 均为**占位或硬编码**（见 §1 表）。
5. **凭据无更新端点**：`routes/credentials.ts` 只有 GET/POST/DELETE，无 PUT；`db`/`cloud` 同理缺 `:id` GET/PUT。
6. **`clusters` 种子项不可达**：种子 `cluster-prod` `connected:false` 且无凭据，点详情必 502。
7. **TopBar 告警数恒 0**：`alertCount` 默认 0，未接 `/alerts` 实时计数。

### 2.4 主题 / UI 一致性（视觉割裂 + 死 CSS）

1. **【视觉不一致】`STATUS_COLOR` 与主题令牌冲突** — `shared/constants.ts:11` `STATUS_COLOR = {ok:'#2E7D32', warn:'#ED6C02', error:'#D32F2F', unknown:'#9E9E9E'}`（旧 MUI 默认色），而 `design-tokens.json`/主题用 `success:#34D399 / warning:#F59E0B / danger:#F87171`。`StatusBadge` 引用 `STATUS_COLOR`，导致状态徽章颜色与其余 UI（HealthRing/KpiCard/图表）不同源。
2. **【视觉不一致】`Sidebar.tsx` 硬编码另一套蓝**（`#0F1B3D`/`#7C9CFF`），与全局主色 `#3D7BFF` 明显割裂；`Terminal.tsx` 也大量硬编码色值。违反 `design-tokens.css` 自身声明「禁硬编码色值（#fff/#000 除外）」。
3. **【死文件】`design-tokens.css` 与 `styles/index.css` 均未被任何模块 import**（index.html 也无 link）。后果：
   - **Tailwind 完全未接入构建**（唯一含 `@tailwind` 指令的 `styles/index.css` 没被引入），`tailwind.config.js` + 三个 tailwind 依赖是**死配置/死依赖**。
   - `design-tokens.css` 的 CSS 变量真源未被加载，主题实际靠 `theme.ts` 读 `design-tokens.json`（JS）。
4. **浅色主题未接入口**：`design-tokens.json/css` 含完整 light 令牌，但 `buildTheme('light')` 从未调用，Settings 仅展示色块 Chip，无法切换。

### 2.5 构建 / 发布

- **依赖位置正确**：后端 `express/cors/ssh2/mysql2/pg/ioredis/ws/@kubernetes/client-node` 在 `dependencies`；前端 React/MUI/Electron/Vite 在 `devDependencies`（Vite 已打包进 bundle，不会 MODULE_NOT_FOUND）。ADR-001 关于「React/MUI 必须在 dependencies」的担忧对**渲染进程**不成立（被 Vite 打包），仅后端裸模块需在 dependencies——当前已满足。
- **`dev` 脚本**：仅 `vite`；Express 需 `npx tsx src/server/index.ts` 另起。与 README 一致，但与 system_design 验收不符（system_design 过时）。
- **SQLite 未落地**：ADR-001/Spec 锁定 better-sqlite3，`crypto.ts` 明确注释「不用 better-sqlite3，纯 JS 零编译」。即升级方案被推翻，回退到 JSON 文件持久化（重启不丢，但无时序查询）。
- **`.env.example` 存在**（✓），`PORT`/`NODE_ENV` 有示例。

### 2.7 类型 / 契约

- 诊断 `engine.ts` 自定义 `Status/Metric/DiagnoseResult`，与 `shared/types.ts` 结构兼容但未复用（双真源）。
- `THEME_TOKEN`（`constants.ts`）写死旧 light 值 `#1E3A8A/#F5F7FA`，与实际 dark 令牌不符，疑似遗留未用。
- 统一信封 `{code,data,message}` 后端 `response.ts` 一致；但 `fail` 始终 HTTP 200（code 区分成败），前端 `bus.ts` 按 `code!==0` 抛错，两端一致，无问题。

| 🔴 高危 | `monitorService.pingProbe` 命令注入（可本地 RCE） |

## 4. 修复优先级建议

**P0（安全，立即修）**
1. `pingProbe` 改用 `execFile('ping', [..数组..])` 或白名单校验 host，杜绝注入。
2. `cors()` 限制 origin / 写接口加轻量令牌；终端 WS 加认证。

**P1（功能正确性）**
3. `sshService.collectMetrics` 补齐 CPU 采集（`top`/`mpstat` 等）并填充 `HostMetricSample` 的 cpu 字段，使 CPU 告警规则可用。
4. 明确「系统体检=本机」「主机=SSH 远程」的边界，修正页面文案/导航，避免与 PRD 误导。
5. 落地通知渠道（飞书/钉钉/企微/邮件）或显式标注为 P2 缺口。

**P2（一致性 / 清理）**
6. 统一状态色：让 `StatusBadge` 改用主题令牌（删 `STATUS_COLOR` 或与之对齐），清理 Sidebar/Terminal 硬编码色。
7. 清理死依赖/死文件：`zustand`、`tailwindcss/postcss/autoprefixer` + `styles/index.css`、`ipc.ts`；或真正接入 Tailwind/design-tokens.css。
8. 文档治理：指定一份「单一真源」规范（建议以 Spec.md v2.0 为准），其余标记 `deprecated` 或删除；修正 README 的 API 机制描述与 `app://`/`ops://` 命名。
9. 凭据补 PUT、clusters 种子补默认凭据或改可达、TopBar 接实时告警数。
